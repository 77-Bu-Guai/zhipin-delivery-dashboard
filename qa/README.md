# BOSS 投递分析 · 测试与缺陷协同工作流

> 本文件是 boss 项目（React18 + TS + Vite + Electron 桌面应用）的测试/Bug 全生命周期总入口。
> 服务对象：测试、研发、产品三方，覆盖「测试准备 → Bug 反馈 → 研发定位 → 修复验证 → 测试验收 → 质量复盘」六个阶段。
> 定位：不是流程文档摆设，而是每个阶段都有**可填的模板 + 明确的负责人 + 阻断判定标准**。

---

## 一、角色与职责

| 角色 | 核心职责 | 在流程里的关键动作 |
|------|----------|--------------------|
| 测试 | 保障交付质量 | 写用例、执行、报 Bug、回归、出验收结论 |
| 研发 | 解决问题、保代码质量 | 定位、修复、补修复说明、配合回归 |
| 产品 | 定义价值与边界 | 出 PRD/需求、定验收标准、拍板上线 |
| 资深开发（质量把关） | 拉高团队技术水位 | 评审 PR、守自动化门禁、沉淀研发 Checklist |

> 小团队一人兼多角时，必须**在文档里显式写明谁扮演哪个角色**，避免「我以为你测了」。

## 二、六阶段生命周期

```
① 测试准备 ──► ② Bug 反馈 ──► ③ 研发定位 ──► ④ 修复验证 ──► ⑤ 测试验收 ──► ⑥ 质量复盘
   写用例          归档问题        给线索           回归               拍板               沉淀
    ↓                                                                              ↓
    └──────────────────────────── 下一版本需求 ───────────────────────────────┘
```

| 阶段 | 输入 | 产出物 | 模板/位置 |
|------|------|--------|-----------|
| ① 测试准备 | PRD / 需求 / 用户故事 | 测试计划 + 测试用例 + 执行清单 + 风险点 | `phase1-测试准备/` |
| ② Bug 反馈 | 现象 / 报错 | 标准 Bug 单（结构化） | `templates/Bug单模板.md` → `bugs/` |
| ③ 研发定位 | Bug 单 + 日志/代码 | 可能原因 + 排查路径 + 待补信息 | Bug 单「研发定位」区 |
| ④ 修复验证 | 修复说明 | 回归测试清单 + 回归结果 | `templates/回归验证清单模板.md` |
| ⑤ 测试验收 | 全部测试记录 | 验收结论 + 版本质量报告 + 上线风险 | `templates/验收报告模板.md` |
| ⑥ 质量复盘 | 本版全部 Bug | 质量复盘报告 + 改进项 + 规范沉淀 | `templates/质量复盘模板.md` |

## 三、严重程度（Severity）与优先级（Priority）

**严重程度 S（技术影响面）**
- S1 致命：应用崩溃 / 数据丢失 / 核心功能完全不可用 / 安全密钥泄露
- S2 严重：主流程阻断但可绕过 / 数据错误 / major 功能失效
- S3 一般：非核心功能异常 / 体验明显受损
- S4 轻微：UI 错位 / 文案 / 边缘提示

**优先级 P（业务处理顺序）**
- P0 立即处理（当天，可能阻断上线）
- P1 本版本内解决
- P2 下版本排期
- P3  backlog / 接受风险

---

## 四、阻断上线判定标准（资深开发拍板）

满足任一即**阻断上线**，必须产品+资深开发双签确认才可放行：
1. 存在未关闭的 S1 Bug；
2. 核心数据流（SQLite → 图表）出现数据错乱或丢失；
3. AI 中继把 Key 写入打包产物或提交进 git；
4. 评分体系阈值（如 -5000 致命项）与提示词实际值不一致；
5. `tsc -b --noEmit` 或 `vite build` 非零退出；
6. 已知线上事故且无止损/回滚预案。

## 六、提醒事项落地（把「提醒」变成「动作」）

| 阶段 | 原提醒 | 落地的强制动作 |
|------|--------|----------------|
| ① | 用例可上传项目资料库、分配执行 | 用例写进 `phase1-测试准备/测试用例.md`，每条标注负责人 |
| ② | 建事项、分配研发、关联原需求、补附件 | 必填「关联需求/PRD/用例」+ 截图/日志，否则研发可退回 |
| ③ | 证据不足不断言根因 | Bug 单「根因」栏在修复前标 `待定`，仅列「可能原因+依据」 |
| ④ | 更新事项状态、补修复说明、发起回归 | 修复后必填「修复说明+影响范围」，否则测试不回归 |
| ⑤ | 上传验收结论、遗留问题建后续事项 | 验收报告归档，遗留项转新 Bug 或下版需求 |
| ⑥ | 沉淀为测试规范/研发检查清单 | 复盘结论合并进 `研发质量Checklist.md` 与本项目规范 |
