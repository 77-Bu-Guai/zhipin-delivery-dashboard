# 质量复盘模板

> 版本结束后由测试牵头、研发+产品参与。复制为 `qa/复盘-<版本/日期>.md`。
> 目标不是追责，是让下一版少踩同样的坑，并把结论**沉淀为规范**。

```markdown
# 质量复盘 · v＜版本/日期＞

- 复盘日期：YYYY-MM-DD
- 参与人：＜测试 / 研发 / 产品 / 资深开发＞
- 本版 Bug 总数：＜＞  已关闭：＜＞  遗留：＜＞

## 一、Bug 分布
| 模块 | S1 | S2 | S3 | S4 | 合计 |
|------|----|----|----|----|------|
| AI 接口配置 | | | | | |
| 数据/评分 | | | | | |
| 导出 | | | | | |
| 插件 | | | | | |

## 二、问题类型 & 根因分类
| 类型 | 数量 | 典型根因 | 证据 |
|------|------|----------|------|
| 需求歧义 | | ＜＞ | |
| 研发逻辑 | | ＜＞ | |
| 测试漏覆盖 | | ＜＞ | |
| 兼容性 | | ＜＞ | |

## 三、修复效率
- 平均定位耗时 / 平均修复耗时 / 回归轮次（1 轮过 vs 多次打回）

## 四、遗留风险
＜未关 Bug 的影响、技术债、已知脆弱点＞

## 五、问题归因（四维度）
- 流程问题：＜如「缺 PRD 就开干」＞
- 需求问题：＜如「验收标准没对齐」＞
- 研发问题：＜如「边界没处理」＞
- 测试问题：＜如「异常场景漏测」＞

## 六、下一版本改进建议
| 改进项 | 归属 | 落地动作 | 目标版本 |
|--------|------|----------|----------|
| ＜如「AI 中继加单测」＞ | 研发 | ＜写进研发 Checklist＞ | |

## 七、规范沉淀
- [ ] 已更新 `研发质量Checklist.md`：＜哪条＞
- [ ] 已更新测试规范 / 用例库：＜哪条＞
- [ ] 已转为自动化门禁：＜如 tsc + build 必须绿＞
```

## 使用提醒

- 复盘结论必须**落到文件**：改 Checklist、补用例、加门禁，而不是散在群里。
- 重复出现的同类 Bug（如「配置持久化冲突」「评分阈值不一致」）应直接进 `研发质量Checklist.md` 成为强制检查项。
