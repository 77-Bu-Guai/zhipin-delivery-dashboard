# Bug 单模板

> 复制为 `bugs/BUG-<序号>-<模块>-<一句话>.md`。**标 ★ 为必填**，缺项研发有权退回。
> 状态机：新建 → 定位中 → 修复中 → 待回归 → 已回归 → 已关闭 / 已拒绝

```markdown
# BUG-XXX 一句话标题

- Bug ID：BUG-XXX
- 标题：＜一句话说清现象＞
- 来源：测试 / 线上 / 用户反馈
- 发现日期：YYYY-MM-DD
- 报告人：＜姓名＞
- 严重程度：S1 / S2 / S3 / S4
- 优先级：P0 / P1 / P2 / P3
- 是否阻断上线：是 / 否
- 关联需求/PRD/用例：＜PRD-id 或 TC-id＞
- 研发负责人：＜姓名＞
- 当前状态：新建

## ★ 复现环境
- 浏览器/客户端：Chrome 126 / Firefox / Electron 打包版
- 操作系统：Windows 11 / macOS
- 应用版本：git commit 或构建时间
- 屏幕/分辨率：（UI 问题必填）
- 账号信息：（脱敏，仅留角色，如「普通用户 / 管理员」）

## ★ 前置条件
＜进入该页面前的状态、已有数据、配置项＞

## ★ 复现步骤
1. 打开 XX
2. 点击 XX
3. 输入 XX
4. 观察 XX

## ★ 实际结果
＜看到什么错误、报错原文、异常表现＞

## ★ 期望结果
＜应该是什么样＞

## 附件
- 截图/录屏：＜路径或粘贴＞
- 日志：＜控制台报错 / 接口返回 / 应用日志关键行＞

## 影响范围
＜哪些功能/页面/用户受影响，是否数据级＞

## —— 研发定位（修复前填）——
- 可能原因（带依据，不拍脑袋）：
- 排查路径：
- 待补充信息（需要测试/产品给的）：

## 根因（修复后填）
＜定位到的真实原因，标注证据来源：日志/代码行/接口返回＞

## 修复说明（修复后必填）
＜改了哪个文件/函数，为什么这么改，影响范围＞

## 回归结论
＜引用回归清单，原问题是否解决 + 关联功能是否受影响＞
```

## 填写红线

- 没有「复现步骤 + 实际/期望结果」的 Bug 一律退回，研发无法复现就无从修起。
- 「根因」在修复前只能写「待定 + 可能原因 + 依据」，禁止在证据不足时断言根因。
- 涉及线上事故：先在新 BUG 单顶部加 ⚠️，并立即在「影响范围」里确认止损方案与回滚预案。
