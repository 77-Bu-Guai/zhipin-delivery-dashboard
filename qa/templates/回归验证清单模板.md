# 回归验证清单模板

> 由测试在研发给出「修复说明」后填写。复制为 `bugs/BUG-XXX-回归.md` 或附在 Bug 单尾部。
> 原则：不只验证「原问题修没修」，还要验证「修的过程有没有打挂别的功能」。

```markdown
# 回归清单 · BUG-XXX ＜标题＞

- 修复版本：＜commit / 构建时间＞
- 回归执行人：＜姓名＞
- 回归日期：YYYY-MM-DD

## 一、原问题验证（必须 100% 通过）
| 序号 | 验证点（取自 Bug 复现步骤） | 预期 | 结果 | 备注 |
|------|----------------------------|------|------|------|
| R1 | 照原步骤重走一遍 | 现象消失 | 通过/失败 | |

## 二、关联功能影响（改动文件牵扯到的模块）
| 序号 | 受影响功能 | 验证动作 | 结果 | 备注 |
|------|------------|----------|------|------|
| I1 | ＜如 AIProviderSettings 改了 saveAISettings＞ | ＜切供应商后配置是否还在＞ | | |

## 三、边界场景覆盖
| 序号 | 边界 | 验证动作 | 结果 |
|------|------|----------|------|
| B1 | 空配置 / 非法输入 | | |
| B2 | 海量数据（5000+ 条） | | |

## 四、回归结论
- [ ] 原问题解决
- [ ] 关联功能无回归
- [ ] 边界场景通过
- 遗留问题 / 风险点：＜有则写，无则填「无」＞
- 是否可关闭：是 / 否（原因：＜＞）
```

## 使用提醒

- 研发修复后**必须**在 Bug 单补「修复说明 + 影响范围」，否则测试不启动回归。
- 回归结果需回写到 Bug 单「回归结论」并通知产品/测试负责人进入验收。
